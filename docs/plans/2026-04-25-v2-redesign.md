# KeroTrack v2 — Full Refactor to API + SPA, DB-Backed Settings

**Date:** 2026-04-25
**Status:** Draft — for approval
**Author:** Collaborative design (user + Claude Code)
**Supersedes:** the incremental containerisation plan that was prototyped against the v1 repo

---

## 1. Goal

Rebuild KeroTrack as two services — FastAPI backend and SvelteKit frontend — running under `docker compose`, with **all runtime configuration stored in a `settings` table** in SQLite and managed via API + UI. Bootstrap-only values stay in `.env`. Match the structural conventions of the sibling projects (`C:/code/JobTrack`, `C:/code/FinTrack`) so the three projects can be maintained the same way.

The MQTT contract on the wire is preserved exactly so the existing ESP32 display ([KeroTrack-display](https://github.com/MrSiJo/KeroTrack-display)) and Home Assistant integration keep working unchanged.

---

## 2. Guiding decisions

1. **Two services in compose**, FinTrack-style: `backend` (FastAPI on `:9176`) and `frontend` (nginx-served SPA on `:9177`). Cleaner build/restart cycles than a single image; keeps parallels with FinTrack.
2. **Frontend: SvelteKit + TypeScript + Tailwind + shadcn-svelte + ECharts**, built with the Vite static adapter (`@sveltejs/adapter-static`) and served by nginx. Svelte was chosen over React because the data flow is read-mostly with a single user — Svelte's reactivity is a better fit than React for live sensor data and the component count stays small.
3. **API-first.** Backend exposes only JSON. No server-side templates. Frontend talks to backend over HTTP and SSE.
4. **Runtime config lives in DB.** A `settings` table holds typed key/value rows. The backend exposes `GET/PUT /api/settings`. The SvelteKit frontend has a `/settings` page that edits these directly. **`.env` only carries bootstrap secrets** (DB URL, port, `TZ`, `LOG_LEVEL`).
5. **APScheduler runs in-process** in the FastAPI lifespan — replaces all host cron. Schedule expressions are themselves settings so the user can tune them from the UI; the scheduler reloads them when they change.
6. **MQTT subscriber co-located with the API** as an asyncio task started in the lifespan. Uses `aiomqtt` rather than wrapping sync `paho-mqtt`; cleaner under uvicorn. Reconnect/backoff handled by `aiomqtt`'s built-in client.
7. **No Flask, no Plotly, no Socket.IO, no eventlet, no `KeroTrack` system user, no host cron, no systemd units.** All of those are deleted as part of the cutover from v1.
8. **Single-user, local-network app, with login.** v2 ships with the **JobTrack auth pattern** (argon2id + Starlette `SessionMiddleware` + CSRF middleware + first-time `/setup` flow). One user per deployment. See [`ADR-0005`](../adr/0005-auth-pattern.md) for the full decision and rationale; the original "no auth in v2.0" stance is superseded.

### 3.3 Cost analysis topic

Live v1 publishes cost analysis to **`oiltank/cost_analysis`** (with underscore — confirmed against production `config.yaml`). The earlier draft of this spec used `oiltank/costanalysis` without the underscore; that was wrong. v2 keeps `oiltank/cost_analysis` with its underscore and the same payload shape (`analysis_date`, `refill_periods`, `latest_metrics`, `historical_averages`, `efficiency_metrics`, `weather_impact`, `energy_metrics`, `cost_data_stats`). The default for `mqtt.topic_costanalysis` in §5.2 is therefore `"oiltank/cost_analysis"`.

### 3.5 Lock-down test

A golden-path regression test feeds canonical Watchman Sonic Advanced JSON through the v2 ingest pipeline and asserts the **exact** `oiltank/level` and `oiltank/analysis` payload shapes against fixtures captured from the v1 deployment. Any field removal, rename, or type change fails the test.

## 5. Settings model

This is the load-bearing decision in the redesign. Every value that today lives in `config/config.yaml` becomes a row in a `settings` table.

### 5.1 `settings` table schema

```sql
CREATE TABLE settings (
    key         TEXT PRIMARY KEY,
    value       TEXT NOT NULL,           -- JSON-encoded scalar/list/object
    value_type  TEXT NOT NULL,           -- 'string'|'int'|'float'|'bool'|'cron'|'json'|'secret'
    group_name  TEXT NOT NULL,           -- 'tank'|'boiler'|'mqtt'|'analysis'|'detection'|'prices'|'notifications'|'schedule'|'web'|'alerts'|'currency'
    label       TEXT NOT NULL,
    description TEXT,
    is_secret   INTEGER NOT NULL DEFAULT 0,
    updated_at  TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_settings_group ON settings(group_name);

CREATE TABLE setting_changes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    key         TEXT NOT NULL,
    old_value   TEXT,                    -- redacted to '***' for secrets
    new_value   TEXT,                    -- redacted to '***' for secrets
    changed_at  TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    source      TEXT NOT NULL            -- 'api'|'cli'|'migration'|'seed'
);
CREATE INDEX idx_setting_changes_key ON setting_changes(key);
```

- `value` is JSON-encoded so lists (e.g. `apprise_urls`) and floats round-trip without loss.
- `value_type` drives both API serialisation and frontend form rendering.
- `is_secret = 1` → value is **redacted** in `GET /api/settings` (returns `"********"`); `PUT` accepts plaintext.
- `setting_changes` is an audit trail. Secrets log only that they changed, never the value.

### 5.4 Settings service contract (`kerotrack/settings/service.py`)

```python
class SettingsService:
    async def get(self, key: str) -> Any: ...                       # typed value, in-process cache
    async def set(self, key: str, value: Any, source: str) -> None: ...  # validates against schema, audit-logs, fires subscribers
    async def all(self, group: str | None = None) -> list[dict]: ...
    async def reset(self, key: str, source: str) -> None: ...       # revert to schema default
    def on_change(self, pattern: str, callback: Callable) -> None:  # glob, e.g. "schedule.*"
```

In-process cache is invalidated on `set`. Subscribers receive `(key, old, new)` so the scheduler can reload triggers and the MQTT subscriber can reconnect when broker settings change.

### 5.5 Settings API surface

```
GET    /api/settings                    → grouped, typed, secrets redacted
GET    /api/settings/{key}              → one
PUT    /api/settings/{key}              → body: {value: <typed>}
PUT    /api/settings                    → body: {key: value, ...} (bulk save)
POST   /api/settings/{key}/reset        → revert to default
GET    /api/settings/schema             → catalogue for the UI (key/type/group/label/description/default)
GET    /api/settings/changes?key=…&limit=…  → audit log
```

Validation errors return `422` with field-level reasons.

## 6. Backend architecture

### 6.1 Lifespan

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    boot = get_bootstrap()
    engine = init_engine(boot.database_url)
    await ensure_schema(engine)
    await seed_settings_defaults()

    settings = SettingsService()
    pubsub = PubSubBus()
    publisher = MqttPublisher(settings)
    scheduler = SchedulerService(settings, jobs)
    mqtt = MqttIngest(settings, pubsub, publisher)

    scheduler.start()
    mqtt_task = asyncio.create_task(mqtt.run())

    settings.on_change("schedule.*", scheduler.reload)
    settings.on_change("mqtt.*", mqtt.reconnect)

    app.state.settings = settings
    app.state.pubsub = pubsub
    app.state.publisher = publisher

    try:
        yield
    finally:
        scheduler.shutdown()
        mqtt.stop()
        await mqtt_task
        await engine.dispose()
```

### 6.2 MQTT ingest + publish

- Single `aiomqtt.Client` connection used for both subscribe (`mqtt.topic_readings`) and publish (`oiltank/level`, `oiltank/analysis`, `oiltank/costanalysis`).
- On each incoming reading: `recalc.process(payload, settings)` → DB write → `publisher.publish_level(reading)` → `pubsub.publish("reading", row)`.
- `publish_level()` produces the v1-compatible `oiltank/level` JSON (see §3.1) — including `cost_to_fill` as a string.
- Analysis and cost-analysis runs publish to `oiltank/analysis` and `oiltank/costanalysis` after writing to the DB.
- Settings changes for `mqtt.*` trigger a reconnect without process restart.

### 6.3 Scheduler

- APScheduler `AsyncIOScheduler`, single timezone from the `TZ` bootstrap.
- Jobs: `run_analysis`, `run_cost_analysis`, `run_notifier`. Each is a thin wrapper over the corresponding module.
- Triggers come from `schedule.*` settings; `coalesce=True`, `misfire_grace_time=3600` so a missed run still fires when the container comes back up within an hour.
- Manual-trigger endpoint: `POST /api/admin/jobs/{name}/run`.
- Each job records a `last_run_at` and `last_status` in the `settings` table for diagnostics.

### 6.4 Notifier

- Weekly summary every Sunday + monthly summary on the first Sunday — same predicate as v1.
- Refill-aware totals identical to v1.
- Apprise URLs from `notifications.apprise_urls`.
- `POST /api/admin/jobs/notifier/run` accepts `{"test": true}` to force-send (matches `notifier.py --test`).

### 6.5 SSE + pub/sub

- In-process async pub/sub bus.
- `GET /api/stream` is an SSE endpoint subscribing to `reading`, `analysis`, `mqtt_message` channels. Frontend's `EventSource` consumes it.
- No polling, no Socket.IO; replaces eventlet entirely.

### 6.6 Auth + sessions (ADR-0005)

JobTrack-pattern auth, single user per deployment.

**Middleware order in `main.py` (load-bearing — wrong order = subtle bugs):**

```python
app.state.secret_key = bootstrap.app_secret_key
app.add_middleware(SessionMiddleware, secret_key=bootstrap.app_secret_key,
                   https_only=False, same_site="lax")
app.add_middleware(RequireAuthMiddleware)   # 401 outside the exempt set
app.add_middleware(CSRFMiddleware)          # X-CSRF-Token on mutating verbs
```

(Starlette applies middleware in reverse-add order, so the runtime order is
`Session → RequireAuth → CSRF → route`.)

**Models.** New `users` table — `id`, `username UNIQUE`, `password_hash`, `created_at`.
At most one row; the service-level `bootstrap_user` rejects creating a second.

**Hashing.** `argon2.PasswordHasher` defaults (Argon2id). `verify` returns `False`
on any exception — no information leak.

**Routes (`api/routes/auth.py`):**

- `GET /api/setup/status` → `{needs_setup: bool}` — exempt from auth
- `POST /api/setup` → bootstrap the single user; 409 `already_setup` if a user exists
- `POST /api/auth/login` → validate, `request.session["username"] = ...`,
  `request.session["csrf_token"] = secrets.token_hex(32)`, return both
- `GET /api/auth/me` → echo username + CSRF token (lazily mints one if missing — covers
  the post-reload case where the token was only in the original login response)
- `POST /api/auth/logout` → `session.clear()`

**Exempt paths (no auth required):** `/api/health`, `/api/setup/status`, `/api/setup`,
`/api/auth/login`, `/api/auth/logout`. Everything else under `/api/` is gated.

**CSRF.** Mutating verbs (`POST/PUT/PATCH/DELETE`) on `/api/*` outside the CSRF-exempt
set (`/api/setup`, `/api/auth/login`) require a matching `X-CSRF-Token` header.

**Frontend integration.** `lib/stores/auth.ts` mirrors JobTrack's `AuthProvider`:
on boot fetch `/api/setup/status`; if not setup, route to `/setup`; otherwise fetch
`/api/auth/me` to determine login state. The typed `lib/api.ts` client sets
`credentials: "include"` and adds `X-CSRF-Token` for mutating verbs. On `401` from any
route the client calls a registered "on unauthorised" callback that clears the auth
store and pushes the user to `/login`.

## 9. Migration from v1 (mandatory — production data must come across)

Migrating the existing KeroTrack v1 database into v2 is a **first-class deliverable**, not an afterthought. The production v1 DB at `/opt/KeroTrack/data/KeroTrack_data.db` holds years of readings, refill history, and analysis runs that must survive the cutover. The local dev copy at `C:/code/KeroTrack/data/KeroTrack_data.db` (~2.6 MB at time of writing) is the test fixture.

### 9.0 How the developer provides v1 data

The v1 system runs at **`root@172.16.0.14`** (Proxmox LXC, hostname `KeroTrack`), with the live SQLite DB and YAML config in `/opt/KeroTrack/data/` and `/opt/KeroTrack/config/`. The docker host that runs v2 lives separately at `172.16.0.83`. SSH key auth is configured for both from the developer machine.

Three layers, each with a distinct purpose:

1. **Sanitised fixture in the repo** — `backend/tests/fixtures/v1_sample.db` (~50 KB, ~200 readings spanning at least 3 refill periods plus an anomaly day, no PII). Committed. Drives all CI/test runs and the migrator's automated tests. Generated once from the local v1 DB by `scripts/build-fixture.py` (Phase 6 deliverable), which redacts the sensor `id`, free-text fields, and any operator-supplied refill notes. Re-runnable whenever the v1 schema or representative data changes.

2. **Full local copy for realistic dev** — the developer's local copy of the v1 production data lives in `C:/code/KeroTrack-v2/legacy/`, gitignored. As of 2026-04-25 it contains:
   ```
   legacy/
     KeroTrack_data.db          (3.5 MB · 17,297 readings · 2023-06-02 → present)
     config.yaml                (live MQTT broker, real boiler, real Apprise URL)
     historical_deliveries.txt
   ```
   Refresh it from the v1 host with:
   ```bash
   scp root@172.16.0.14:/opt/KeroTrack/data/KeroTrack_data.db \
       root@172.16.0.14:/opt/KeroTrack/data/historical_deliveries.txt \
       root@172.16.0.14:/opt/KeroTrack/config/config.yaml \
       legacy/
   ```
   The migration CLI's `--src-db` / `--src-config` default to looking in `legacy/` in dev so manual rehearsals run against real data without anything sensitive entering the repo.

3. **Production cutover** — at cutover, snapshot the live v1 data from `172.16.0.14` to the docker host `172.16.0.83`, bind-mount that snapshot into the migrator container. Step-by-step in §10.

The fixture is the single source of truth for tests; the `legacy/` copy is for human-in-the-loop validation; the production DB is only ever touched at cutover.

### 9.2 Migration CLI

One-shot CLI inside the backend container:

```bash
docker compose run --rm \
  -v /opt/KeroTrack/data:/app/legacy/data:ro \
  -v /opt/KeroTrack/config:/app/legacy/config:ro \
  backend python -m kerotrack.cli migrate-v1 \
    --src-db /app/legacy/data/KeroTrack_data.db \
    --src-config /app/legacy/config/config.yaml \
    [--dry-run] [--report report.json]
```

What it does, in order:

1. **Pre-flight checks.**
   - Source DB exists, is readable, has expected schema. Aborts with a clear error otherwise.
   - Destination DB exists and has v2 schema applied (it does — `db_migrate.ensure_schema` runs on container startup).
   - Destination is empty for the tables about to be filled, OR `--force` is set. Refuses to silently merge into a non-empty destination.
2. **Schema copy.** Opens v1 SQLite read-only with `mode=ro` URI. For each known table, reads rows in batches and inserts into the v2 DB inside a single transaction per table. Schemas are identical, so no field mapping is needed.
3. **Settings load.** Parses v1 YAML and maps each key to the v2 catalogue (see mapping table below). Writes through `SettingsService.set(..., source="migration")` so changes are audit-logged.
4. **File artefacts.** Copies `price_cache.json` into `/app/data/`. Reads `historical_deliveries.txt` and ensures any deliveries it contains are present in `refill_data` (idempotent — uses delivery date as the key).
5. **Diff report.** Prints (and writes to `--report` if supplied) a structured summary:
   - Row counts per table copied (source → destination, per-table).
   - YAML keys consumed.
   - YAML keys ignored (with a "no v2 equivalent" note).
   - Settings defaulted because the YAML didn't supply them.
   - Any rows skipped (e.g. constraint violations, with the row PK).
6. **Exit code.** Zero on full success. Non-zero if any required setting ended up unset, or if any table failed to copy fully.

`--dry-run` performs steps 1–3 against an in-memory destination and emits the diff report without touching the real DB. Used for cutover rehearsals.

### 9.4 Tests

The migrator must have these tests before it ships:

- **Schema parity** — copy a snapshot of the local dev DB (`C:/code/KeroTrack/data/KeroTrack_data.db`, ~2.6 MB) into a temp source path and run the migrator end-to-end into a temp v2 DB. Assert row counts match per table.

- **Tolerant of missing tables** — exercise a v1 DB with only `readings` populated; migration succeeds and the diff reports the empty tables explicitly.

## 12. Risks & mitigations

- **MQTT contract breakage breaks KeroTrack-display.** Mitigation: golden-path regression tests with fixture JSON captured from the v1 deployment cover every field on `oiltank/level` and `oiltank/analysis`. CI must run them on every PR.
- **DB migration data loss.** Mitigation: migration is read-only against v1 DB; v2 writes to a separate named volume; keep a 30-day tarball of `KeroTrack_data.db`.
- **Settings drift across deployments.** Mitigation: defaults live in code (`schema.py` + `seeds.py`). Seeding is idempotent and only inserts missing keys — never overwrites operator changes. New settings ship with sane defaults.
- **Secret-in-DB exposure.** SQLite is on a Docker volume on the host; same exposure as v1's `config.yaml`. Mitigation: secrets redacted in `GET /api/settings`; `setting_changes` audit log doesn't store full secret values. Plain at-rest encryption is *not* in v2 scope.
- **APScheduler missed runs across container downtime.** Mitigation: `coalesce=True`, `misfire_grace_time=3600`, plus a `last_run_at` stamp per job in the `settings` table so the notifier can detect "I should have run yesterday and didn't".
- **`aiomqtt` vs `paho` parity.** Mitigation: golden-path tests cover the input/output contract end-to-end before the rewrite touches any field. Reconnect/backoff handled by the library.
- **Auth in v2.** Single-user JobTrack-pattern auth (ADR-0005). Trade-off: a login screen on every fresh deploy and an `APP_SECRET_KEY` to manage. Mitigated by the first-time `/setup` flow so there's no manual SQL to bootstrap the user.
- **SQLite + Windows host bind-mounts.** Mitigation: production uses a *named* Docker volume (compose already does this). Don't bind-mount the DB on Windows for dev — keep it on a named volume there too.

## 15. Phase workflow & deployment

This is a **standing instruction** for every plan in this repo, including the implementation plans that descend from this one. It is intentional and authorised by the project owner.

### 15.1 Per-phase ritual

A "phase" is a numbered chunk of work in a plan (e.g. "Task 4: MQTT ingest port"). On completing a phase:

1. **Tests green.** All applicable test layers pass locally: `pytest backend/tests`, `npm --prefix frontend test`, plus any phase-specific Playwright runs.
2. **Commit straight to `main`.** Sentence-case imperative summaries (e.g. `Add aiomqtt ingest task with settings-driven reconnect`). No feature branches, no PR review gate — single-maintainer project, the trunk is the working set.
3. **Push to `origin/main`.** `git push` — that is the trigger.
4. **Deploy.** Run the deploy command (§15.3) from the local working tree against the remote Docker host. The build + push happens over the SSH-bound Docker context, so the local image goes straight onto the server.
5. **Verify.** Hit `http://172.16.0.83:9176/api/health` (backend) and `http://172.16.0.83:9177` (frontend). Confirm `mqtt_connected: true` once MQTT is wired up. For data-affecting phases also confirm KeroTrack-display still updates.
6. **Update the phase status in the plan** (`Status: Done` line on the phase header) and commit-and-push that too.

### 15.2 Docker context (one-time setup, on the developer machine)

Run this once per workstation. The context lives in the user's Docker config, not in the repo:

```bash
docker context create docker-host --docker "host=ssh://root@172.16.0.83"
docker context use docker-host
```

After this, every subsequent `docker` / `docker compose` call from this shell targets the remote host until the context is switched back (`docker context use default`).

The SSH key for `root@172.16.0.83` is already configured on the developer machine — Docker reuses it transparently. **No additional auth setup is required.** If a key prompt ever appears, it means the SSH agent has lost the key, not that the workflow needs new credentials.

### 15.3 Deploy command (every phase push)

From the repo root, with the docker-host context active:

```bash
docker compose --env-file .env up -d --build
```

That single command:

- builds the backend image from `backend/Dockerfile` on the remote host
- builds the frontend image from `frontend/Dockerfile` on the remote host (`VITE_API_URL` baked in from `.env`)
- (re)starts both services, attached to the named volumes `kerotrack-data` and `kerotrack-logs`
- leaves them running detached

The first run on a host also creates the network and volumes. Subsequent runs reuse them.

### 15.4 Port assignments

Random-ish, deliberately non-overlapping with the sibling projects on the same host:

| Project | Service | Port |
|---|---|---|
| FinTrack | API | 7433 |
| FinTrack | UI | 7432 |
| JobTrack | combined | 8747 |
| **KeroTrack v2** | **backend (API)** | **9176** |
| **KeroTrack v2** | **frontend (UI)** | **9177** |

`.env` carries these as `BACKEND_PORT` / `FRONTEND_PORT` so they can be overridden per environment without editing `compose.yaml`.

### 15.5 Rollback

If a deploy goes sideways:

```bash
git revert HEAD
git push
docker compose --env-file .env up -d --build
```

Volumes survive the redeploy, so application state is preserved. If a migration phase corrupted state, restore the v1 tarball or a previous v2 volume snapshot before redeploying.

### 15.6 What this ritual replaces

- No GitHub Actions / no CI pipeline (yet — can be added later, but the trunk-based push-to-deploy loop is the source of truth).
- No staging environment — there's one host, one deployment.
- No PR review — single-maintainer project, all reviews are by the maintainer ahead of the commit.

If/when this changes (e.g. CI added, second maintainer joins), supersede this section with a new ADR.
